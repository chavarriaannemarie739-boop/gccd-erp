# 仓库权限细化设计

> 状态：已确认并实现  

> 日期：2026-08-06  
> 范围：管理后台（`yarn/yarn` + `gccd_server`）仓库相关菜单与数据权限

---

## 1. 背景与目标

现场需要按仓库职责授权，例如：

- 张三：圆钢档案 + 圆钢库存 + 圆钢入库，同时负责**成品发货**（与圆钢入库可为同一人）
- 李四：配件档案 + 配件库存 + 配件出入库
- 另可配置成品仓管：成品档案 + 成品库存 + 成品出入库
- 管理员：全部可见

成功标准：

1. 后台给用户/角色**勾选菜单权限**即可组合职责，不必写死「一人一仓」。
2. 无权限的仓库 Tab **不显示**（不是点进去再报错）。
3. 接口按允许的仓库/物料属性过滤，避免改请求参数看到别仓数据。
4. 超级管理员（`is_super=1` 或 `user_id=1`）不受限。

---

## 2. 非目标（这期不做）

- 不新建独立的「角色-仓库绑定」新权限体系表（可后续演进）。
- 不把「圆钢库存 / 配件库存 / 成品库存」拆成三个独立页面；仍共用现有页，按权限显隐 Tab。
- 不改造小程序端仓库权限（若小程序有同类入口，另开需求）。
- 不在这期强制打开全站 `ApiVerifyMiddleware` 菜单鉴权（可列为后续加固项）。

---

## 3. 权限模型

### 3.1 两层控制

| 层 | 作用 | 实现 |
|----|------|------|
| 菜单/按钮 | 决定「能不能进这个功能」 | 现有 `ya_system_menu` + 角色菜单勾选 |
| 仓库数据范围 | 决定「进了之后能看哪类仓/物料」 | 由已授权菜单推导允许的仓库类型；超管不限 |

### 3.2 可勾选功能块（菜单粒度）

| 功能块 | 说明 | 推导出的仓库范围 |
|--------|------|------------------|
| 圆钢档案 | 物料档案-圆钢 | 圆钢 |
| 配件档案 | 物料档案-配件 | 配件 |
| 成品档案 | 物料档案-成品 | 成品 |
| 圆钢库存 | 物料库存中的圆钢能力 | 圆钢 |
| 配件库存 | 物料库存中的配件能力 | 配件 |
| 成品库存 | 物料库存中的成品能力 | 成品 |
| 圆钢入库 | 入库中的圆钢能力 | 圆钢 |
| 配件入库 | 入库中的配件能力 | 配件 |
| 成品入库 | 入库中的成品能力 | 成品 |
| 配件出库 | 出库中的配件能力 | 配件 |
| 成品出库 | 出库中的成品能力 | 成品 |
| 成品发货 | 发货单 | 成品（发货业务；不自动打开成品库存 Tab，除非另勾成品库存） |
| （其它非仓库菜单） | 不参与仓库范围推导 | — |

说明：

- **同一用户可同时勾多项**。例如：圆钢档案 + 圆钢库存 + 圆钢入库 + 成品发货。
- 出入库是否开放，完全由是否勾选对应菜单决定（圆钢角色可不给出库）。

### 3.3 允许仓库范围的推导规则

引入统一能力（建议抽到公共方法，替代仅靠角色名映射）：

```
allowedWarehouses = 从用户已授权的仓库相关 menu_url / 菜单标识 推导的并集
若用户是超管 → allowedWarehouses = 全部（不过滤）
若非超管且未命中任何仓库相关权限 → 仓库类列表为空（或仅显示无数据，禁止看仓）
```

仓库类型枚举：`圆钢` / `配件` / `成品`  
与现网字段兼容映射保持不变（复用 `InStockService` 已有 LIKE 集合）：

- 圆钢 ← `圆钢仓库` / `圆钢库` / `原料库` / `原料仓库`
- 配件 ← `配件仓库` / `配件库`
- 成品 ← `成品仓库` / `成品库` / `成品仓`

**兼容策略：** 现有按角色名（`配件库`/`圆钢库`/`成品库` 等）的映射保留为补充来源，与菜单推导取**并集**，避免旧角色突然失权。

## 4. 菜单改造

### 4.1 现状问题

- 「配件档案 / 圆钢档案 / 成品档案」共用同一 `menu_url`：`admin/production.Material/list`，无法靠 URL 区分类型。
- 「物料库存 / 入库 / 出库」是单页多 Tab，菜单只有一份，无法表达「只开圆钢库存」。

### 4.2 改造方式

1. **档案菜单**：为三类档案配置可区分的权限标识（推荐新增 `menu_url` 或扩展权限码），例如：
   - `admin/production.Material/listRoundSteel`
   - `admin/production.Material/listAccessory`
   - `admin/production.Material/listProduct`  
   后端 `list` 仍走同一接口，但根据权限强制 `material_property`；或增加轻量校验：无对应权限则拒绝该 property 查询。

2. **库存 / 入库 / 出库**：增加**按钮级或虚拟菜单权限码**（`menu_type=2`），用于勾选与推导，不必各建一套完整页面路由：
   - 例：`warehouse.scope.roundSteel` / `warehouse.scope.accessory` / `warehouse.scope.product`  
   - 或更细：`warehouse.inventory.roundSteel`、`warehouse.inbound.roundSteel`、`warehouse.outbound.accessory` …  
   推荐**细粒度**（库存/入库/出库分开），以便「有圆钢入库、无圆钢出库」。

3. **成品发货**：沿用现有发货单菜单（`admin/production.Ship/list`），单独勾选，可与圆钢入库同时赋给同一人。

4. **角色预置（可选配置，非代码写死）**：
   - 角色「圆钢库」：默认勾圆钢档案+库存+入库（出库按需）
   - 角色「配件库」：默认勾配件档案+库存+出入库
   - 角色「成品库」：默认勾成品档案+库存+出入库  
   实际以管理员在角色/用户上的勾选为准；跨仓职责通过多勾或多角色并集实现。

## 5. 后端改动点

| 模块 | 改动 |
|------|------|
| 公共 | 新增/扩展「当前用户允许的仓库类型 / material_property」查询（菜单权限 ∪ 旧角色名映射；超管放行） |
| 入库 `InStock/list` | 已有限仓 → 改为走新推导；无权限的仓不可查 |
| 库存 `InStock/mateiallist`（及库存相关） | 接入同样过滤 |
| 出库 `OutStock/list` | 接入同样过滤 |
| 物料档案 `Material/list` | 按权限限制可查的 `material_property`（圆钢/配件/成品） |
| 发货 `Ship/list` | 无发货菜单权限则不可用（菜单层）；数据层若需可按成品范围约束（这期以菜单控制为主） |
| 写入类（入库新增等） | 无对应仓权限时拒绝写入；默认仓取用户允许仓的交集 |

| 页面 | 改动 |

## 8. 验收要点

1. 非超管只勾圆钢相关时：库存/入库页无配件、成品 Tab；接口查配件仓返回空或无权限。
2. 同一账号勾「圆钢入库 + 成品发货」：两者菜单都在，库存若未勾成品库存则仍无成品库存 Tab。
3. 只勾配件出入库、不勾配件档案：可进出出入库，不能进配件档案。
4. 超管行为与现网一致，三仓都可见。
5. 旧角色名「配件库/圆钢库/成品库」用户升级后不丢仓权限（并集兼容）。

---

## 9. 风险与回滚

- **风险**：菜单权限码变更后，旧角色需补勾新按钮权限，否则可能暂时看不到 Tab。  
  **缓解**：发布时提供角色菜单补丁 SQL；兼容旧角色名映射。
- **回滚**：前后端开关或回退「仅超管/角色名」旧逻辑；菜单 SQL 可逆。

---

## 10. 实施顺序建议

1. 后端：统一 `warehouse_scopes` 推导 + 库存/出入库/档案过滤  
2. 用户信息接口下发 scopes  
3. 前端：三页 Tab 显隐  
4. 菜单/权限码与角色补丁 SQL  
5. 用张三/李四/超管账号验收

## 11. 已确认决策

| 项 | 结论 |
|----|------|
| Tab 无权限时 | 不显示（非报错） |
| 管理员 | 看全部 |
| 成品仓 | 这期纳入，可单独配 |
| 圆钢入库与成品发货 | 可为同一人，靠菜单多勾 |
| 实现路径 | 菜单勾选 + 按仓数据过滤（不新建完整数据权限体系） |
