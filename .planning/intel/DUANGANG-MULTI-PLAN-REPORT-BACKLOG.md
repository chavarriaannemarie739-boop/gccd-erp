# 断钢多计划同规格 — 报工选单混淆 & 流转卡扫码方案备忘

> **状态**：已讨论、已记录，**暂不开发**。用户确认当前报工上限逻辑正确，无需修改。  
> **记录日期**：2026-06-11  
> **触发案例**：`scjh-202606060003`、`scjh-202606060004`

---

## 一、问题描述

两个生产计划**成品不同**，但**圆钢相同、客户相同**；在断钢工序物理上都要断成 **50×1.2**。

断钢工人**只管断**，不关心后续穿孔成什么成品型号。报工时经常在小程序工单列表里**分不清该报哪个计划**，导致：

- 报错计划 → 一计划超报、另一计划缺数；
- 或触发后端校验：`当前工序累计报工数量不能超过计划数量(task_num)`。

---

## 二、根因（业务 vs 系统）

| 现场操作粒度 | 系统记账粒度 |
|--------------|--------------|
| 圆钢 + 断钢产出规格（如 50×1.2） | 一个 `product_task` = 一个生产计划 + 一种成品 |

小程序工单卡片展示：计划名称、计划单号、圆钢、断钢型号、**成品型号**。  
对断钢而言前几项常几乎相同，**成品型号**又是工人最不关心的字段 → 列表选单天然易混。

**报工上限（已确认正确、不改）**：`ProductReportService::report()` 按**工序累计**与工单 `task_num` 比较，严格 `>` 拦截（计划 200 可报到 200，不能 201）。

---

## 三、零开发阶段可做的现场措施（已讨论）

1. **计划命名规范**：名称含现场可辨批次（A批/B批、班次、日期），勿两计划同名。
2. **班组长派工表**：料垛 ↔ 计划单号 ↔ 今日可报余量，开工前明确。
3. **物理标识**：断钢产出按垛挂卡/贴签，与计划一一对应；**没卡不报、混堆不报**。
4. **排产习惯**：同圆钢同断钢规格尽量错开并行计划，减少列表重复项。
5. **善用现有筛选**：圆钢 + 断钢筛完后若仍多条，必须对照计划名称/单号与派工表。

---

## 四、倾向方案：流转卡 + 二维码扫码报工

用户讨论结论：**对该场景非常理想的方向之一**（前提是流程跟得上）。

### 为何适合

- 把「猜计划」变成「扫哪垛料就是哪个计划」→ **1:1 绑定**，几乎不会选错。
- 与现有按 `product_task` 报工、计划数上限逻辑**兼容**，不必先改合并报工模型。
- 符合制造业流转卡习惯；穿孔及后续工序可沿用同卡扩展追溯。

### 落地前提（不做则效果打折）

| 要点 | 约定 |
|------|------|
| 一卡对应什么 | **一垛料 / 一次下推批次一张卡**（非整计划一大卡） |
| 何时发卡 | 计划下推或断钢领料时打印，与料垛同挂 |
| 卡面信息 | 客户简称、计划简称、圆钢、断钢规格、计划吨数；二维码供系统读 |
| 混料 | 两计划料不得混堆 |
| 异常 | 补打/作废旧码、丢卡权限；无网时可用计划单号后四位兜底 |

### 方案对比（简）

| 方案 | 评价 |
|------|------|
| 命名 + 白板派工 | 零开发，靠人，并行多时仍混 |
| 列表优化 / 智能推荐 | 仍要选，有误点风险 |
| 断钢合并报工再分摊 | 最贴「只管断」，模型改动大 |
| **流转卡 + 扫码** | 开发量中等，**现场确定性最高**，推荐为中期主路径 |

**推荐路线**：短期现场规范止血 → 中期 **工序专属选单 + 扫码报工** → 并行计划极多再评估合并报工。

## 六、若开发时的功能要点（备忘，未排期）

- 计划下推或领料时**打印流转卡**（含二维码，编码建议：`task_id` 或 `task_code` + 校验）。
- 小程序：**扫码 → 直达该工单报工页**（可弱化/隐藏同质列表选单）。
- 断钢工序列表可按「圆钢 + 断钢规格」分组，组内仅作兜底。
- 补打卡、作废码、扫已关闭工单提示。
- 可选：穿孔沿用同一张流转卡扫码。
